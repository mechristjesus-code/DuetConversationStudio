### Important storage distinction

The database should describe media; it should not contain entire video files as ordinary database records. Large media belongs in the filesystem, with database records pointing to its managed path and recording metadata.

Imported videos should be treated as read-only originals. Exports and temporary render files should go into separate directories.

The application must resolve its storage paths relative to a configured project root, not rely on whichever directory happens to be active in the Termux shell.

### 5\. Existing API and route map

These routes were identified in the earlier project review. They are the known API inventory, not a guarantee that each route has passed a live request-and-response test.

| Route                   | Intended responsibility                            |
| ----------------------- | -------------------------------------------------- |
| GET /                   | Serve the studio interface                         |
| GET /media/             | Serve or retrieve permitted media                  |
| GET /api/assets         | List registered media assets                       |
| GET /api/segments       | List editing segments                              |
| GET /api/turns          | List conversation turns and response relationships |
| GET /api/generations    | List generated video records                       |
| POST /api/assets/upload | Register or upload an asset                        |
| POST /api/render/duet   | Create a duet render                               |
| POST /api/turns         | Record a new conversation turn                     |

The next API additions should be based on gaps discovered during inspection, not added automatically. Potential future endpoints include project creation, project retrieval, export-job status, cancellation, and a local communication queue.

### API rules

* Validate file types, sizes, paths and clip boundaries.

* Never let an API request read arbitrary files outside approved storage locations.

* Do not treat a browser-supplied file path as trusted.

* Return explicit error codes and actionable messages.

* Record export status as pending, running, succeeded, failed or cancelled.

* Avoid running expensive FFmpeg jobs synchronously in a request handler if doing so makes the server unresponsive.

For local-only use, bind the server to `127.0.0.1` by default. Network access from other devices should be a separate, explicitly configured capability.

### 6\. Database and conversation-history model

The four known tables give us a useful starting point.

`assets`

Media inventory

Identifies each source or generated media file, with metadata such as duration, format, checksum and storage reference where supported by the existing schema.

`segments`

Editing instructions

Records clip selections and timing, including the relationship to the relevant source asset.

`conversation_turns`

Conversation lineage

Represents a participant's contribution or response, with links to its related media and parent turn where implemented.

`generations`

Rendered outputs

Tracks an export's input relationships, render instructions, output location and status where supported.

Every generated video must retain its own record and references to its inputs. Re-editing a duet should create a new revision or generation instead of silently overwriting its history. This lets us reconstruct how a conversation evolved and which source files contributed to each output.

### 7\. Video-processing pipeline

The editing pipeline should follow a predictable sequence:

* Import and inspect

    Select two local videos, inspect their format, duration, dimensions, frame rate, audio streams and readability using FFprobe.

* Choose the clips

    Set the start and end points for A and B. Validate that the requested ranges are inside the source durations.

* Configure the duet

    Choose side-by-side or alternating playback, output aspect ratio, clip order, audio levels and whether to preserve the original soundtracks.

* Build the render instructions

    Generate a validated FFmpeg filter graph. Normalize incompatible dimensions, pixel formats, frame rates and audio streams where necessary.

* Render to a temporary file

    Write to `media/temp/` using a unique job identifier. Do not overwrite a previous successful export.

* Validate the result

    Check FFmpeg's exit status, inspect the output with FFprobe, verify the expected streams and confirm the output file is readable.

* Publish the export

    Move the validated file into `media/exports/`, record the generation and input lineage, and show the user a playable result.

### 8\. Communication and collaboration subsystem

The communication subsystem should remain independent of the rendering pipeline. A failed email or unavailable network must never prevent a local video export.

### Proposed local communication queue

1\. Intake

Record that a video is ready, feedback is needed, or a participant has a pending response.

2\. Review

Show the recipient, purpose, linked video and proposed message before anything leaves the device.

3\. Prepare

Create a message draft or open the user's chosen mail workflow, including Proton Mail if supported.

4\. Human approval

Require explicit review and approval before sending a message or performing another external action.

5\. Status and history

Record queued, reviewed, prepared, sent if verifiable, cancelled or failed. Never label an unsent draft as sent.

### Optional Resend integration

Resend could later provide a transactional email delivery service for notifications or collaboration messages. It is not the video editor, not a conversation database, and not a replacement for Proton Mail.

If you choose it later, the architecture should place it behind a dedicated mail adapter. API keys must stay on the backend, outside frontend files, and every external send must follow the application's approval policy. Resend setup is not a prerequisite for the first working MP4.

### 9\. Future AI and conversation intelligence

The AI layer should consume the history the editor already records. It should not be allowed to rewrite original video files or alter the authoritative editing history.

Stage A — Transcription

Generate transcripts from permitted audio, attach timestamps, and retain links to the original source. Keep uncertain words and speaker attribution marked as uncertain.

Stage B — Conversation search

Search transcripts, participants, video relationships, editing history and conversation topics. Use local indexing where practical.

Stage C — Offline AI

Add a model adapter for an available local inference engine. The editor must still work if the model is missing, stopped or out of memory.

Stage D — Reviewed learning data

Create explicitly approved training examples, with provenance, consent, quality checks, exclusion controls and versioned datasets before considering model training.

A critical distinction: saving conversations, searching them, and using them as training data are three different operations. The first two do not automatically train a model. Any future training pipeline must have its own dataset approval and versioning process.

TikTok should initially be treated as an external source from which the user may obtain permitted media. Direct platform integration should wait until the supported access methods, terms and permissions have been verified.

### 10\. Installation and runtime boundaries

The application is designed for the phone-only Termux environment. The prior preflight identified Python 3.14.6, Node.js 26.4.0, FFmpeg/FFprobe 9.0.2 and Git. The SQLite command-line program was not installed, but Python's built-in `sqlite3` module can provide database access if its availability is confirmed.

| Component                  | Responsibility                                         |
| -------------------------- | ------------------------------------------------------ |
| Termux                     | Run the local application and media engine             |
| Python backend             | API, project data, validation and job coordination     |
| SQLite                     | Structured project history and metadata                |
| FFmpeg / FFprobe           | Video and audio processing                             |
| HTML, CSS, JavaScript      | Phone-friendly interface                               |
| Android browser or WebView | Display and interact with the studio                   |
| Optional AI engine         | Transcription, retrieval and inference in later phases |

No Android Studio is required for the first PWA-based milestone.

Important: Android shared-storage permissions, browser file-selection behavior, background process restrictions and available memory all need to be tested on the actual device. We should not assume the PWA can access arbitrary Android files or that a long-running export will survive the operating system suspending Termux.

### 11\. Security and data-preservation rules

These are the project's operating rules, not optional future features.

* Keep Duet Conversation Studio independent of Galaxy Mind, LUNA and Script Library.

* Preserve the existing project and inspect Git status before modifying tracked files.

* Keep original video sources unchanged.

* Keep generated exports, temporary files, and source files separate.

* Use parameterized SQL queries and validate every incoming request.

* Restrict file operations to approved storage locations.

* Keep secrets and email API keys out of frontend code, Git and logs.

* Require approval for external messages, uploads and other consequential actions.

* Provide cancellation for queued or running jobs where technically possible.

* Avoid silent overwrites and destructive migrations.

* Create and verify a backup before a database migration or substantial change.

* Record changes, test results and known limitations in the project documentation.

### 15\. Definition of success

The first release is successful when you can open the studio on your phone, select two real videos, edit them, export a playable MP4, close the studio, reopen it, and recover the project with its editing instructions intact.

The larger architecture remains ready to grow, but the first release does not depend on AI, TikTok integration, cloud services, email delivery or a new APK.

The governing principle is simple: build a working local editor first, preserve every relationship and revision, and add communication and intelligence without compromising the foundation.
